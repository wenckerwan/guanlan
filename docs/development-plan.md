# 观澜开发规划（开发标准）

本文件是**开发标准**：定义下一步做什么、按什么顺序做、每项怎么算做完。
任何后续开发都应先在本文件中找到对应条目，再动手写代码。

配套文件：

- [../README.md](../README.md)：开发规范（版本规则、分支策略、提交规范、同步清单）。
- [../CHANGELOG.md](../CHANGELOG.md)：版本事实记录，只写实际做过并验证过的事。
- [release-roadmap.md](release-roadmap.md)：早期版本路线（V0.1-dev.1 ~ V0.2，历史存档）。
- [website-roadmap.md](website-roadmap.md)：站点现状与内容来源映射（快照）。

> 状态标记：`待开始` / `进行中` / `已完成` / `阻塞`。
> 条目只有在「完成标准」逐条满足、并把实际验证输出写进 CHANGELOG 后才能标 `已完成`。

## 一、开发优先级原则

按以下顺序决策，不要跳级：

1. **解除阻塞** — 先恢复容器验证能力，否则后面所有阶段都无法判定「做完」。
2. **补真实缺口** — 只做用户能感知到的缺失，不做「顺手重构」。
3. **打通数据链路** — 内容从只读源目录到站点的通路必须可对账、可重跑。
4. **增强体验** — 检索、练习、统计。
5. **上线加固** — 缓存、备份、权限、监控。

同一阶段内，优先做**依赖更少、能独立验证**的条目。

## 七、每项任务的固定流程

任何条目开工到收尾，都必须走完：

1. **认领** — 在本文件对应条目写入负责人与开始日期。
2. **建分支** — `feature/<topic>`、`fix/<topic>` 或 `docs/<topic>`。
3. **写测试** — 先写会失败的测试，再写实现。
4. **本地验证** — 跑 `tools/verify.ps1`（离线）。
5. **容器验证** — 跑 `lint.sh` + `smoke.sh`（若 B1 已解除）。
6. **更新 `VERSION`** — 有实际变更才提升。
7. **更新 `CHANGELOG.md`** — 粘贴**实际**命令输出，不写「应该通过」。
8. **检查 `git diff`** — 确认无 `node_modules`、缓存、临时日志、原始私有资料、密钥。
9. **提交** — 提交信息含版本或版本后缀，如 `feat: add pagination for V0.1-dev.4`。
10. **合并与打标** — 合并 `main`，打小写 Git tag。

## 八、验收总则

一个条目算「完成」，必须同时满足：

- 「完成标准」每一条都能指到具体产物或命令输出。
- `CHANGELOG.md` 里有对应的**实际**验证记录。
- 没有把「已知限制」里的问题伪装成已解决。
- 新增的纯逻辑有测试覆盖；新增的接口有冒烟用例。

以下情形**不算完成**：

- 「本地看着没问题」但没跑验证命令。
- 只跑了离线检查却声称容器可用。
- 把阻塞项跳过、留到后面「一起验」。
