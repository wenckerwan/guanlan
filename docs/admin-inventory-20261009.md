# 管理后台盘点与开发顺序

日期：2026-10-09。基准：`main` / `ff5329b`，沿用当前生产玻璃 UI。

## 1. 核查范围与结论

本次逐页检查 `apps/web/pages/admin`、后台路由、AdminController、AdminService、文章资源、认证中间件、文章与试卷导入脚本。后台已有 10 个业务入口和 1 个承载导航及权限提示的入口文件，不需要重新搭建全部后台。

这是代码盘点，并辅以公开 HTTP 抽查；没有登录管理员账号、读取生产用户资料或在生产执行写操作，不代表全部功能已通过真实数据验收。没有修改业务代码或部署。

公开抽查结果：`/admin` 返回 200；`/api/v1/admin/overview`、`/api/v1/admin/users`、`/api/v1/admin/hotspots` 对无凭据请求均返回 401。普通用户的 403、管理员成功读写及数据不变检查尚未执行。

9 月 29 日后台计划中的部分缺口已经有实现，应以本次代码核查更新认识，不能继续按旧文档称真题、错题画像、复习统计等页面不存在。

## 2. 页面能力清单

| 页面 | 代码已有能力 | 当前缺口 | 建议顺序 |
|---|---|---|---|
| 总览 `overview.vue` | 内容计数、今日新增用户、14 天注册与作答趋势、发布状态分布、学习排行、最近用户及审计 | 主请求失败只设置 null，趋势仍按空数据补零；没有统一加载、失败、重试状态；缺日期范围、访问统计整合与明确定义的活跃指标 | 第 4 阶段 |
| 用户 `users.vue` | 邮箱/昵称搜索、创建账号、角色与用户组调整、启停、错题编号绑定、重置密码 | 默认最多 50 条，无分页与真实总数；缺角色/状态筛选和用户详情；角色与禁用操作直接执行；没有最后一个有效管理员保护；密码输入为明文文本 | 第 1、2 阶段 |

| 分析 `analysis.vue` | 新增、删除、发布/隐藏、评论模式设置 | 默认最多 100 条；没有正文编辑入口；缺搜索、分类筛选、分页、删除确认和预览 | 第 1、3 阶段 |

| 预测 `predictions.vue` | 分页、发布/隐藏、评论模式；服务端还能调整排序 | 页面没有正文编辑、新建/删除、搜索、层级筛选和排序编辑；目前定位是导入内容的上下线管理 | 第 3 阶段 |
| 错题 `mistakes.vue` | 考生与绑定信息、条目分页、模块/错误类型/行动建议编辑、Markdown 画像上传与预览、按考生复习汇总 | 考生列表无分页/检索；条目 API 调用未传模块或错误类型筛选；复习、条目及画像部分加载失败回退为空或默认内容；全局字段编辑需明确影响范围 | 第 2、3 阶段 |
| 评论 `comments.vue` | 按状态/文章类型筛选、分页、审核、置顶/取消、删除并确认 | 缺关键词、指定文章、用户、时间范围筛选及文章上下文跳转；缺批量审核 | 第 3 阶段 |
| 审计 `audit-logs.vue` | 分页、按操作前缀筛选、显示时间/操作人/对象/摘要 | API 已支持 adminId，但页面无操作人筛选；没有时间范围/对象筛选；详情按字段截取 40 字；缺完整详情查看；操作标签未覆盖预测和评论等已有日志 | 第 2、4 阶段 |

全局：现有横向导航与各页面表格、表单可以继续复用。加载、成功、失败、空列表、保存中、重试和危险操作确认处理不一致，应先统一行为，再做布局细节。移动端实际可用性未做浏览器验证。

当前没有独立后台页面的扩展项：资料文档管理、AI 系统配置、数据集对账、备份/健康状态。旧计划提到其中多项；本次仅确认后台页面和 admin 路由组缺少对应入口，不能由此断言其他模块或运维通道完全没有这些能力。作答记录已有 `/admin/attempts` API，但没有独立明细页，可在统计阶段增加筛选和下钻。上述扩展项应单独定需求，不作为第一批开发的必选范围。

## 3. 应优先处理的实际问题

### 3.1 后台编辑与离线导入会相互覆盖

证据：`apps/api/seeders/ArticleSeeder.php` 中分析、预测通过 DatasetReader::truncate 清空，时政删除所有非空 slug 后再导入；`PaperQuestionSeeder.php` 删除试卷与题目后重建。后台手工内容、正文改动、上下线状态可能被后续对应导入覆盖；新建时政也会生成非空 slug。

先定义内容来源与更新优先级，再增加编辑功能：稳定业务标识、区分数据集与后台内容、记录修订、导入前显示差异及冲突、明确哪些字段由后台管理。禁止默认为后台新增和维护的数据仍可安全地通过全量清空导入。

验收：后台新建内容、隐藏内容、修改正文后执行测试环境导入，记录仍存在且维护字段按明确策略保留；源数据合法更新能同步；发生冲突时明确提示，不静默覆盖。验证数据 ID 变化对收藏、评论及作答引用的影响。

### 3.2 部分修改接口的行为不符合编辑预期

证据：`AdminService::saveHotspot/saveAnalysis` 找不到更新 ID 时会创建新记录；请求不带 status 时直接 normalize(null) 为 published，因此编辑隐藏文章的其他字段可能重新发布。当前前端状态切换会携带 status，此问题主要影响后续完整编辑入口及直接 API 调用。

要求：更新不存在记录返回 404；部分更新只修改实际提供的字段；状态非法返回明确校验错误；保留已有状态；校验标题与正文等字段，统一 HTML 处理和元信息生成规则。当前仅有 published/hidden，草稿需单独设计而不能直接传 draft。

验收：隐藏文章只改标题仍隐藏；无效 ID 不产生新记录；非法状态返回 422 且数据不变；正文更新后的目录与字数一致。

### 3.3 管理员账号操作缺少防误操作规则

证据：用户页直接切换角色和状态；`AdminService::updateUser` 没有最后一个有效管理员保护；resetPassword 只更新密码哈希，没有撤销已有 UserToken。Auth::resolve 每次检查用户 active，因此禁用后的既有令牌会被拒绝，这项已有能力应保留。

建议：危险操作确认；服务端防止最后一个有效管理员被禁用或降权，并处理并发；重置密码后撤销现有会话；自己降权后的界面与会话及时更新；密码默认遮罩且可显式切换显示。重置密码撤销会话属于建议的新规则，需要纳入实施设计。

验收：最后管理员保护不能只在页面实现；并发请求不会把有效管理员数量降为零；禁用、降权及重置后的会话行为符合规则；日志不记录密码或令牌。

### 3.4 列表截断和错误状态会误导操作

证据：用户标题用 items.length 作为总数，服务默认 limit 50；时政与分析同样用返回数组长度，默认 limit 100；押题固定 page=1/perPage=20；总览及部分错题请求失败会显示空结果。

要求：统一分页响应与真实 total、可复现的筛选、稳定排序；区分尚未加载、加载中、请求失败、确实为空；失败不展示伪造零统计或默认内容，保留重试入口；保存时防止重复提交。

验收：构造超过 50/100/20 条的测试数据，各页能够完整访问；接口失败显示错误与重试；筛选变化重置页码；删除最后一条能回退至有效页。

## 4. 推荐开发顺序

### 第 1 阶段：保存可靠性与账号操作保护

先修部分更新/404/状态校验、删除事务和危险操作确认，补管理员保护与密码重置会话规则；明确数据集导入与后台维护的冲突策略，并在测试环境验证。保留现有后台入口和玻璃主题。

这是后续完整编辑和批量操作的前提。应有普通用户越权 403、匿名 401、管理员正向、非法请求数据不变及并发保护测试。

### 第 2 阶段：统一列表与反馈

用户、时政、分析服务分页；补押题翻页和真题题目翻页；统一搜索筛选、真实总数、加载/失败/空状态、保存中、提示和重试；错题考生检索；补审计完整详情与已有 API 操作人筛选。

第一批页面可选用户与时政，提炼共用表格、分页、筛选、确认和状态组件后推广。共用组件服从现有业务，不重写整个后台框架。

### 第 3 阶段：内容维护流程

时政、分析先补管理员正文详情读取接口（现有列表不返回 html）、完整编辑表单、Markdown 编辑与预览、来源/修订记录及安全渲染，再扩展题目新增与内容对账、预测排序/编辑、错题筛选和评论定位。草稿、发布确认、批量操作在规则确定后增加。

模拟卷及预测是否支持后台全文编辑，应在第 1 阶段的数据来源规则中明确；避免为本来只读的导入内容先搭建无法持久保存的编辑界面。

### 第 4 阶段：统计与运营

整合已有访问统计，严格标明是访问次数而非人数；补日期筛选、注册/学习/作答指标定义、时区与更新时间、详情下钻；扩展审计时间/对象查询及必要导出。活跃用户、留存等新指标先确认数据足够再做，不能按现有总数推算。

### 第 5 阶段：后台布局完善与真实验收

在上述组件稳定后改善导航分组、表单密度、移动端表格、键盘操作与焦点提示。通过管理员真实数据的查看—编辑—保存—前台读取流程，覆盖非管理员拒绝、请求失败、重复提交、筛选翻页和并发；上线前备份，发布后核对公开页面与后台结果。

## 5. 开发范围选择

| 路线 | 优点 | 代价 | 建议 |
|---|---|---|---|
| 先修可靠性，再逐页补功能 | 避免编辑丢失与误发布，共用行为统一 | 外观变化最初较少 | 推荐 |
| 先做后台布局 | 能尽快看见视觉改善 | 数据截断与编辑覆盖问题仍存在 | 可作为独立视觉任务 |
| 一次重写整个后台 | 有较大布局自由度 | 覆盖范围大，现有功能回归成本高 | 当前不建议 |

建议下一项具体任务为「第 1 阶段：后台保存可靠性与危险操作保护」。本报告仅提出开发次序，不把新功能建议视为已经确定的实现需求。
