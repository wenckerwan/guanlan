## 结论

未通过，暂不应以“注册流程可用”对外开放。真实验证码邮件发送失败，未完成“收信 → 注册 → 登录”闭环。本轮只做验收与隔离诊断，未修改或部署注册代码。

## 实测

使用已连接 Gmail 邮箱的唯一测试别名，直接操作生产注册页面，无 API 拦截或伪造响应。

通过的项目：

- 注册页正常显示邮箱、6 位验证码、密码与可选昵称。
- 浏览器表单阻止未填验证码提交。
- 后端拒绝过短密码（422）和缺失验证码（409）。
- 线上邮箱验证功能确实开启，配置了两个发信账号。
- 两个发信账号均通过真实 SMTP TLS 连接和 AUTH LOGIN，返回 235；因此不是账号密码失效或 465 端口不可达。

失败的项目：

- 点击“获取验证码”后未得到正常 JSON 成功响应，返回 HTML 错误页面；页面显示“验证码发送失败，请稍后重试”。
- 公网请求在网关日志中显示约 60 秒后连接结束（499）。仅凭此日志不能确定外层错误页的具体 HTTP 状态。
- 数据库生成验证码记录，但 Gmail 对测试别名的 inbox/spam/trash 全范围搜索未发现验证码邮件。
- 因未收到真实验证码，没有绕过校验或人为注入验证码创建账号。因此成功注册、自动登录、退出后重新登录、重复注册等后续步骤尚未验收。

## 根因定位

故障位置：`apps/api/src/Support/Mailer.php` 的 `swooleTransport()`，尤其是第 188 行调用 `sslHandshake()` 的路径。

在当前 API 容器的独立 PHP 进程内，以协程上下文直接调用现有传输初始化方法，打印连接开始后发生核心转储，未完成连接。生产服务主容器仍为 running/healthy，重启计数为 0；该健康状态不足以证明邮件业务正常。

对照实验在另一个独立 PHP 进程内，先用 `setProtocol(['open_ssl' => true, 'ssl_host_name' => $host])` 初始化 TLS，再连接已配置的 465 端口，约 0.26 秒连接成功，并收到 SMTP 220 横幅。实验仅连接与退出，没有发送额外邮件，也没有替换运行中的服务代码。

下一步应修复协程 TLS 初始化，并验证 465 隐式 TLS 与 587 STARTTLS 各自的初始化和握手顺序；随后重新执行真实收信、注册、自动登录、刷新恢复、退出再登录及异常验证码验收。对照实验成功不等于完整发信或注册已修复。
